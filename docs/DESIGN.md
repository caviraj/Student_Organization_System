## 1. Tech Stack
| Layer | Choice |
|---|---|
| Frontend | React 19 + TypeScript + Vite, Tailwind CSS, React Router, TanStack Query, Zod, `qrcode.react`, `html5-qrcode` (scanner), Recharts |
| Backend | Python 3.11+, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2, PyJWT, `bcrypt` (used directly; `passlib` dropped — it is unmaintained and its bcrypt backend lags bcrypt 4.x), APScheduler (reminder job) |
| DB | PostgreSQL (Supabase-hosted). **Two URLs, and they are not interchangeable:** `DATABASE_URL` points at the **transaction pooler** (port 6543) and is what the running API uses — prepared statements disabled, `sslmode=require`, small pool; `DIRECT_URL` points at the **session pooler / direct connection** (port 5432) and is used by Alembic and `scripts/seed.py` only. Tests use `TEST_DATABASE_URL`, a different database. Postgres-only: UUID, JSONB, TIMESTAMPTZ — no SQLite anywhere in app code |
| DB safety | Every table in `public` has **RLS enabled with no policies** (migration `275474077f1c…`): Supabase publishes `public` over its own REST API, and RLS-on-with-no-policies is what keeps that door shut. The backend is the table owner, so it is unaffected; `FORCE ROW LEVEL SECURITY` is never used. No advisory locks or session-level state anywhere (the transaction pooler may hand each statement to a different backend); `SELECT … FOR UPDATE SKIP LOCKED` inside one transaction is the concurrency tool. `scripts/check_db.py` exits non-zero if any table has RLS off |
| Storage | Supabase Storage (receipts, banners, product images) |
| Payments | `PaymentProvider` interface → `MockProvider` (dev/tests), `RazorpayProvider` (real). Selected by `PAYMENTS_PROVIDER` |
| Hosting (demo) | Frontend: Vercel · Backend: Render/Railway · DB: Supabase |
| Tests | pytest + httpx (backend), Vitest + Testing Library (frontend) |

## 3. Architecture
```
React SPA ──HTTPS/JSON──> FastAPI ──SQLAlchemy──> Postgres
                              ├── services/payments  (Mock → Razorpay)
                              ├── services/ledger    (auto income entries)
                              ├── jobs/reminders     (daily expiry scan)
                              └── Supabase Storage   (uploads)
```
**Core idea:** everything that costs money is an **Order** → has a **Payment** → on success creates **Fulfilment** (membership / tickets / merch reservation) **and** a **Ledger transaction**. Expenses are the only outflow. Therefore the treasurer's numbers always reconcile.

## 4. Data Model (PostgreSQL)
All money = `INTEGER` paise. All PKs = UUID. All tables: `created_at`, `updated_at`.

**users**: id, email (unique), password_hash, full_name, phone, department, year, role (`admin|treasurer|organizer|volunteer|member|guest`), member_code (unique, e.g. `SSA-2026-0042`), email_opt_in, is_active

**membership_plans**: id, name, price, duration_months, ticket_discount_pct, merch_discount_pct, description, is_active

**memberships**: id, user_id→users, plan_id→plans, status (`pending|active|expired|cancelled`), start_date, end_date, order_id→orders, renewal_reminded_at
  *constraint:* `unique(user_id)` — one membership row per member; renewals extend it (past orders keep the purchase trail). The member's QR card is therefore always a single, current code.

**events**: id, title, description, venue, starts_at, ends_at, banner_url, status (`draft|published|closed`), created_by

**ticket_types**: id, event_id, name, member_price, non_member_price, capacity, sold_count, sale_starts_at, sale_ends_at
  *constraint:* `sold_count <= capacity`, plus `capacity > 0`, `sold_count >= 0` and both prices `>= 0` — the database refuses an oversell even if a future caller forgets rule 2.

**orders**: id, user_id, kind (`membership|ticket|merch`), status (`pending|paid|failed|cancelled|refunded`), subtotal, discount, total, currency=`INR`, meta JSONB, idempotency_key

**order_items**: id, order_id, item_type (`plan|ticket_type|variant`), item_id, quantity, unit_price, line_total

**payments**: id, order_id, provider (`mock|razorpay`), provider_ref, status (`created|succeeded|failed`), amount, raw JSONB

**tickets**: id, order_id, event_id, ticket_type_id, user_id, code (unique, short random), status (`valid|used|void`), price_paid, is_member_price, checked_in_at, checked_in_by
  *constraint:* `code` unique+indexed, and an index on `(event_id, status)` so the door counters and the report stay cheap. `price_paid`/`is_member_price` are **frozen at purchase time**, so a later price change or lapsed membership never rewrites history.

**announcements**: id, title, body, category (`meeting|deadline|change|general`), audience (`all|members|event`), event_id?, is_pinned (default false), author_id, published_at, revision_note, edited_at?
  *constraint:* `event_id` is required when `audience='event'` and refused otherwise; at most **3** rows may have `is_pinned` at once. There is **no DELETE** — the record of what was said, and when, is permanent.

**announcement_revisions** (immutable history): id, announcement_id→announcements, title, body, category, audience, edited_by→users, edited_at, note
  *meaning:* a row stores the **previous** version each time an announcement is edited — so `announcements` is always current and the revisions read as the trail behind it. Rows are never updated or deleted.

**announcement_deliveries**: id, announcement_id, user_id, channel (`email|inapp`), status (`queued|sent|failed`), attempts (default 0, max 3), error?, sent_at
  *constraint:* `unique(announcement_id, user_id, channel)` — one delivery per person per channel, which is what makes the worker safe to run twice. Indexed on `(status, channel)` (the worker's claim) and `(announcement_id)` (the admin view). An `inapp` row is delivered by being in the feed: the worker marks it `sent` without calling a provider, so in-app delivery cannot fail.

**products**: id, name, description, image_url, base_price, member_discount_pct, is_active
  *meaning:* `base_price` is what a non-member pays; `member_discount_pct` is the product's own member discount (0–100). A member pays the **better** of this and their plan's `merch_discount_pct` (§4 rule 12).

**product_variants**: id, product_id→products, size, color?, sku, stock, low_stock_threshold
  *constraint:* `stock >= 0`, `low_stock_threshold >= 0`, and `unique(product_id, size, color)` — one row per size/colour on a product (colour is `NULL` for a one-colour product, so the constraint uses `NULLS NOT DISTINCT` to stop a second colourless row of the same size). `sku` is unique and the **stock is only ever changed by a stock movement** (§4 rule 12): checkout, release, restock and manual adjustment all write one `stock_movements` row in the same transaction, so the shelf and the audit trail can never disagree.

**stock_movements** (immutable audit trail): id, variant_id→product_variants, delta (signed), reason (`initial|sale|release|restock|adjustment`), order_id→orders?, created_by→users?, note?
  *meaning:* append-only — rows are never updated or deleted, and there is no endpoint that writes one directly. `initial` is written with the variant (the opening stock), `sale` at checkout, `release` when a dead order gives stock back, `restock`/`adjustment` for an admin's manual change. **Invariant, asserted by the tests and by `scripts/seed.py`: `SUM(stock_movements.delta) == product_variants.stock`** for every variant. Visible via `GET /variants/{id}/stock-movements`.

**merch_orders** (extension of orders for fulfilment): order_id PK→orders, fulfilment_status (`paid|packed|handed_over`), delivery_method (`pickup|campus_delivery`), delivery_note?, packed_at?, handed_over_at?, handled_by→users?
  *meaning:* a row exists **only once a merch order is paid**, and is created inside the payment transaction starting at `paid`. The buyer's choice of `delivery_method` and `delivery_note` is captured in `orders.meta` at checkout and copied here on success, so the fulfilment board never depends on parsing `meta`. Delivery info is a merch concern, which is why it lives here and not on `orders`.

**fundraisers**: id, title (indexed), description?, goal_amount (`> 0`), event_date (indexed), status (`planning|active|done`, default `planning`), owner_id→users, completed_at?
  *meaning:* the club's own money-raising plan — a bake sale, a stall, a book drive. `owner_id` is the organizer who answers for it: only the owner (or an admin) may change it, so one person cannot quietly re-date someone else's stall. There is **no DELETE**: a fundraiser that happened is a fact, and its ledger rows need a parent.

**tasks**: id, fundraiser_id→fundraisers?, event_id→events?, title 3–120, description?, category (`baking|supplies|table_duty|promotion|other`), assignee_id→users?, due_date?, status (`todo|doing|done`, default `todo`), position, completed_at?, created_by→users
  *constraint:* `fundraiser_id IS NOT NULL OR event_id IS NOT NULL` — a card always hangs off a board, so `position` (its slot in a column) is never ambiguous. Indexed on `(fundraiser_id, status)`, `(assignee_id, status)` and `(due_date)` — the board, "my cards" and the overdue filter each get their own path. `position` is rewritten **densely** whenever a card moves, which is what makes a drag-and-drop drop land where the user let go.

**task_activity** (immutable trail): id, task_id→tasks?, actor_id→users, action (`created|status_changed|assigned|edited|due_changed`), from_value?, to_value?, created_at
  *meaning:* append-only — there is no endpoint that writes one directly, because every change goes through `services/tasks.update_task`/`move_task`, which writes the row in the same transaction. `task_id` is `ON DELETE SET NULL`, so deleting a card keeps the trail and the final row remembers the title it carried. A status change is `todo → doing`, an assignment is a user id → a user id, a due-date change is an ISO date → an ISO date, and an edit to any other field is the field name → `null`.

**transactions** (ledger): id, direction (`in|out`), amount, source (`dues|tickets|merch|fundraiser|other_income|other_expense|expense_reimbursement`), ref_type, ref_id, event_id?, fundraiser_id?, occurred_at, note, logged_by→users?, idempotency_key?, is_reversal (default false), reverses_id?→transactions
  *meaning:* append-only — **no UPDATE and no DELETE of an amount anywhere in the code**, which is what makes the treasurer's numbers worth trusting. `logged_by` and `idempotency_key` were added in Phase 5 for the one entry a human types by hand (income against a fundraiser): every row now records its author, and `unique(fundraiser_id, idempotency_key)` is what turns a double-click into a replay instead of a second row. Existing rows keep `NULL` keys, and Postgres treats those as distinct, so the constraint is free to add.
  *Phase 6:* `source` gained `other_expense` (the value lives in a Python tuple rendered as `VARCHAR`, so no DDL was needed) and the table gained `is_reversal`/`reverses_id`. **A reversal is a second row that undoes the first**, never an edit: `reverses_id` is **UNIQUE**, so a row can be reversed at most once and a double-click on "reverse" resolves at the database, not in a service (409 `ALREADY_REVERSED`). A reversal cannot itself be reversed (409 `NOT_REVERSIBLE`), and only the two hand-typed sources (`other_income`, `other_expense`) may be reversed at all — a ticket sale is undone by a refund, not by rewriting history. Every total subtracts a reversal from the side its original was on (§4 rule 14), which is why `is_reversal` is indexed. A partial unique index `uq_transactions_manual_idem` on `idempotency_key` (where the source is a manual one) is what makes a retried hand-typed entry a replay: Phase 5's key is scoped to a fundraiser, so it cannot guard a row that has none.

**expenses**: id, claimant_id→users, amount (`> 0`, 1–50,000 rupees per claim), description (5–300), category (`supplies|food|printing|venue|travel|marketing|equipment|other`), incurred_on (today, or up to 90 days back), event_id?→events, fundraiser_id?→fundraisers, receipt_path? (bucket key, **never a URL**), receipt_mime?, receipt_size?, status (`submitted|approved|rejected|reimbursed|withdrawn`, default `submitted`), reviewed_by?→users, reviewed_at?, review_note?, reimbursed_by?→users, reimbursed_at?, reimbursement_method? (`cash|upi|bank_transfer`), reimbursement_reference?, ledger_transaction_id?→transactions
  *constraint:* `amount > 0`, and `NOT (event_id IS NOT NULL AND fundraiser_id IS NOT NULL)` — a claim is charged to an event **or** a fundraiser, never both, or the same rupees would be counted twice in `by-event` and `by-fundraiser`. Indexed on `(claimant_id, status)` (a volunteer's own list), `(status, created_at)` (the treasurer's queue), and `event_id`/`fundraiser_id` (the per-dimension totals).
  *meaning:* `ledger_transaction_id` is the **link between a claim and the one `out` row that paid it**, written in the same transaction as the ledger row (§4 rule 14). It stays `NULL` until the claim is reimbursed, and it is what `reconcile()` walks to prove no reimbursed claim was paid twice or not at all. `reimbursement_method`/`reimbursement_reference` record *how* the money left — a UPI reference is the treasurer's only defence when a volunteer says the transfer never arrived.

**expense_history** (immutable trail): id, expense_id→expenses (ON DELETE CASCADE), actor_id?→users, action (`submitted|resubmitted|edited|receipt_attached|approved|rejected|reimbursed|withdrawn`), note?, created_at
  *meaning:* append-only, and there is no endpoint that writes one directly — every change goes through `services/expenses.py`, which writes the row in the same transaction. Unlike `task_activity` it cascades with its parent: a claim has no meaning without the claim, and nothing else references a history row. It is what makes "rejected, fixed, resubmitted, approved" readable months later, and the only place the rejection note survives after a resubmission clears `review_note`.

**finance_periods**: id, name (unique, 3–120), start_date, end_date, status (`closed|reopened`, default `closed`), closing_balance (paise, **frozen at closing time**), snapshot JSONB (the semester report as it stood), closed_by?→users, closed_at, reopened_by?→users, reopened_at?, reopen_reason?
  *constraint:* `end_date >= start_date`, `name` unique (409 `PERIOD_NAME_TAKEN`), and a closed period may not overlap another closed one (409 `PERIOD_OVERLAP` with the name of the one in the way).
  *meaning:* a signed-off stretch of the books. Once closed, `services/ledger.add_transaction` refuses to write any row dated inside it (409 `PERIOD_CLOSED`), so the number a treasurer reported cannot move under them. Closing requires the period to be in the past and the books to reconcile, and refuses while claims dated inside it are unsettled (409 `PENDING_CLAIMS`) unless an **admin** forces it — a treasurer reaching for `force` gets 403. Reopening is admin-only and the reason (10+ chars) is kept: the person who froze the books cannot quietly unfreeze them. A reopened period is **kept**, not deleted — the fact that it was reopened is itself the record.

**reminders**: id, membership_id, kind (`expiry_30|expiry_7|expired`), created_at, delivered (bool)
  *constraint:* `unique(membership_id, kind)` — the idempotency guard that makes "at most one reminder per kind per membership" (rule 6) structural rather than a hope. A renewal deletes the membership's reminders, opening a fresh cycle for the new term.

### Key rules (enforce in services, covered by tests)
1. **Price rule:** member price iff user has `active` membership at purchase time; discounts from the plan perks apply to merch.
2. **No oversell:** `UPDATE ticket_types SET sold_count = sold_count + :q WHERE id=:id AND sold_count + :q <= capacity` (0 rows → 409 `SOLD_OUT`). Same pattern for `product_variants.stock`.
3. **Payment success handler is idempotent** and, in ONE DB transaction: marks order paid → creates fulfilment → writes ledger `in` row. The `M2` Razorpay handler keys off `provider_ref`; the `M1` mock handler has no gateway callback to dedupe on, so it claims the order first — `UPDATE orders SET status='paid' WHERE id=:id AND status='pending'` — and a 0-row result means "already settled", so the caller replays the stored result instead of repeating the work. Both are the same idea: the conditional UPDATE is the lock.
4. **Check-in:** `UPDATE tickets SET status='used', checked_in_at=now() WHERE code=:c AND status='valid' AND event_id=:e` — row count decides valid vs already-used.
5. **Expense** can be `approved` only if a receipt is attached; `reimbursed` creates ledger `out` row. Narrowed in Phase 6 to that one sentence — naming, visibility, the review decision and the payment are rule 14.
6. Membership expiry job (daily; `services.reminders.run_expiry_scan()` so tests can drive it directly): `active` & `end_date < today` → `expired` **and** an `expired` reminder; otherwise `active` & `end_date <= today+30d` → `expiry_30` reminder, plus `expiry_7` once it is within 7 days. At most one reminder per kind per membership, enforced by the unique constraint — so a scan that runs twice in a day is a no-op. Returns `{scanned, expired, reminders_created}`.
   **Academic year:** `end_date = start_date + plan.duration_months` only. The "cap to the academic year end" from the PRD is deliberately not applied — a one-year plan bought in month 3 would otherwise silently grant only 9 months. Revisit if the club decides dues are per-academic-year rather than rolling.
7. **Activation (part of the rule-3 transaction):** on a successful membership payment the member's `memberships` row goes `active`, `renewal_reminded_at` resets, its old reminders are cleared, a `member_code` is minted if the user has none (`SSA-<year>-NNNN`, sequential within the year), and the role is promoted `guest → member` **only** — paying dues can never demote a volunteer, organizer, treasurer or admin whose role was set deliberately.
8. **Ticket fulfilment (part of the rule-3 transaction):** a successful ticket payment marks the order `paid`, issues exactly `quantity` tickets with unique 10-character codes, and writes one ledger `in` row (`source=tickets`, `ref_type=order`, `event_id` from the order's meta). Idempotent twice over: the pending→paid claim guards a replayed callback, and the ticket issuer returns the existing tickets rather than minting more. Codes use an unambiguous alphabet (`ABCDEFGHJKMNPQRSTUVWXYZ23456789` — no `0/O/1/I/L`) because volunteers read them aloud at the door. Rule 1 applies at checkout, not at payment: the price is resolved and frozen when the order is created.
9. **Seats are reserved at checkout, not at payment** (so two shoppers cannot both be told there is one seat left), and released when the order dies: `mock-confirm {outcome:"fail"}` marks it `failed`, and a sweep every 5 minutes cancels ticket orders still `pending` after 15 minutes (`services.tickets.release_expired_pending_orders()`, called by the scheduler and directly by tests). Release never pushes `sold_count` below 0. A **free** ticket type skips payment entirely — seats reserved, tickets issued, no payment row and **no ledger row**, because nothing was earned.
10. **Announcement visibility is one filter, applied everywhere** (`services.announcements.visibility_clause`): guest → `audience='all'`; active member → `all` + `members`; anyone signed in who holds a `valid` **or** `used` ticket for the event → that event's `audience='event'` posts; organizer and above → everything. A post the caller may not see answers **404, never 403** — the existence of a members-only post is itself members-only news. Posting resolves the audience to recipients and writes all delivery rows in the **same transaction** as the post; a change to `title`/`body`/`category` requires `revision_note` (3+ chars) and copies the replaced version into `announcement_revisions` first, while `audience`/`event_id` are frozen after posting (422 `AUDIENCE_LOCKED`). Pin toggles need no note but still obey the limit of 3 (409 `PIN_LIMIT_REACHED`).
11. **Delivery worker** (`services.delivery_worker.process_queued_deliveries`): claims up to 100 `queued` rows with `SELECT … FOR UPDATE SKIP LOCKED` in one transaction (so two workers never send the same mail), sends `inapp` by marking it `sent`, and calls the email provider for the rest. Success → `sent` + `sent_at`; failure → `attempts += 1` + `error`, still `queued` until `attempts` reaches 3, then `failed` for good. A recipient who opted out after their mail was queued is marked `failed` with the reason rather than mailed. Idempotent: a second pass over the same rows sends nothing. Run by a 60-second APScheduler job **and** once immediately after a post via `BackgroundTasks`. Email is console-only in M1 (`EMAIL_PROVIDER=console`; any address at `fail.test` raises), behind the `EmailProvider` interface, so M2 swaps in a real sender without touching the worker.
12. **Merchandise** (`services/pricing.resolve_merch_unit_price`, `services.inventory`, `services/merch`):
    - **Member price** = `base_price` less the **larger** of `product.member_discount_pct` and the caller's **active** plan's `merch_discount_pct` (source `product` or `plan`), rounded half-up in integer paise: `unit_price = (base_price * (100 - pct) + 50) // 100`. No floats anywhere in the path. A guest, or a member whose membership has expired, pays `base_price`. The price is resolved and frozen on the `order_items` row at checkout, exactly like tickets — a later price change or lapse never rewrites an order. `MERCH_MEMBERS_ONLY=true` (default) requires an **active** membership to check out at all: 403 `MEMBERSHIP_REQUIRED`, which is the club's "merch is a member perk" rule and is one setting away from being switched off.
    - **Stock is reserved at checkout, not at payment** (the same reason as rule 9): `UPDATE product_variants SET stock = stock - :q WHERE id = :id AND stock >= :q AND is_active` — 0 rows → 409 `OUT_OF_STOCK` with `details {variant_id, product_name, size, available, requested}`. Lines are sorted by variant id so two overlapping checkouts always take row locks in the same order (no deadlock 500s), and the whole multi-line cart lives in the **one** order transaction: if line 3 is short, lines 1 and 2 are rolled back with it — never a half-reserved cart. Each line writes a `sale` movement. Limits: at most 5 lines and 1–5 per line (422 above that) — a cap on how much one person can take off a shelf that is only ever a few dozen units.
    - **Release** gives a dead order's stock back with a `release` movement, idempotent by marker: the order row is locked `FOR UPDATE`, then `orders.meta.stock_released` is checked, so a payment failure and the sweep racing over the same order cannot both credit the stock back. It happens when `mock-confirm {outcome:"fail"}` marks the order `failed`, and when the every-5-minute sweep (`services.merch.release_expired_pending_merch_orders`, same 15-minute TTL, `SKIP LOCKED`) cancels merch orders still `pending`. Confirming an order the sweep already cancelled → 409 `ORDER_NOT_PAYABLE`, so a late tap on the gateway cannot resurrect an order whose stock is gone; an already-*failed* order that is replayed (either outcome) changes nothing and releases nothing further.
    - **Fulfilment** (`merch_orders`) is created by the payment success handler inside rule 3's single transaction, at `paid`, with the ledger row (`source=merch`, `ref_type=order`, note `Merch sale - <items>`). It is idempotent twice over: the pending→paid claim stops a replayed confirmation, and `fulfil_merch_order` returns the existing row rather than creating a second one. So paying twice reserves once, credits the ledger once, and never takes a second item off the shelf. Fulfilment moves **forwards, one step at a time** — `paid → packed → handed_over`, 409 `INVALID_TRANSITION` with `details {from, to, allowed}` for anything else (including re-setting the current status) — and `packed_at`/`handed_over_at` record when it happened.
    - **Manual stock changes** (`adjust_stock`) are a conditional UPDATE too — `WHERE stock + delta >= 0` — so a write-off below zero is 409 `NEGATIVE_STOCK`, not a CHECK-constraint 500. `restock` and `adjustment` are the admin's only ways to move stock by hand; `PATCH /variants/{id}` deliberately cannot set `stock`.
    - **Stock status** is derived, never stored: `out_of_stock` at 0, `low` at 0 < stock ≤ `low_stock_threshold`, else `in_stock`. `GET /admin/merch/stock-summary` reports per product and per size what is on the shelf, what **sold** (units on `paid` orders) and what is merely **reserved** (units on `pending` orders, i.e. in someone's cart), plus demand by size — which is what tells you which size to reorder.
13. **Fundraisers, the task board and hand-logged income** (`services/fundraisers.py`, `services/tasks.py`, `services/income.py`):
    - **Lifecycle is one way:** `planning → active → done`, and `done` is final — `planning → done` is 409 `INVALID_TRANSITION` (a plan that never ran is not a finished one), as is any move backwards. Closing with cards still open is 409 `OPEN_TASKS` with `details {open_count}` unless `force=true`, which exists because a stall sometimes closes with one poster never put up. A `done` fundraiser's board is **read-only** (409 `FUNDRAISER_CLOSED`), but income stays open for **7 days after `completed_at`** — the cash box is counted the same evening, and five people each report their takings at different times.
    - **Every card change leaves a trail:** the organizer and above may change anything, but the **assignee owns exactly one thing — the column their own card sits in** (403 `FORBIDDEN` for anything else, and for anyone else's card). Setting `status` to `done` stamps `completed_at`, and reopening clears it. `position` is rewritten densely across both the column left behind and the column landed in, and an impossible slot is clamped rather than refused — the card always lands somewhere sensible.
    - **Health is a named rule, not a vibe** (`health_of`, constants in the service): `done` ⇒ `completed`; otherwise **behind** if 3+ cards are overdue, or the event is ≤ 3 days away with under 70% done, or the date has passed; **at_risk** if 1+ overdue, or 2+ cards are unassigned, or the event is ≤ 7 days away with under half done; else **on_track**. The thresholds are constants so the frontend's colours and the backend's word for it cannot drift apart.
    - **Income is the one ledger entry a human types, so it is the one that can be typed twice.** `POST /fundraisers/{id}/income` writes one `in` row (`source=fundraiser`) and honours an `Idempotency-Key`: the same key replays the row it already wrote (`replayed: true`) instead of counting the cash again. The guard is `unique(fundraiser_id, idempotency_key)` — the lookup is a courtesy, the constraint is the real one, and two requests racing past the lookup resolve by re-reading the winner's row. `raised` is always the SUM of the fundraiser's `in` rows, never a stored counter. Amounts are 1 paise–Rs 1,00,000 (one stall's cash box, not a bank transfer), and an entry may be backdated up to 30 days but never dated in the future.
    - **There is no edit or delete for income, a task delete is the only way a card disappears, and nothing here deletes a fundraiser.** `DELETE /tasks/{id}` writes its own `edited`/`deleted` activity row first, so the trail survives the card (`task_activity.task_id` goes `NULL`, the title stays in `to_value`).
14. **Expense claims, receipts and the treasurer's books** (`services/expenses.py`, `services/finance.py`, `services/storage.py`, `services/ledger.py`):
    - **Money leaves the ledger exactly once, and one writer is what makes that true.** `services/ledger.add_transaction(...)` is the *only* function in the codebase that constructs a `Transaction` (a test reads every file under `app/` and fails if any other module does). It refuses `amount <= 0`, an unknown direction or source (422 `VALIDATION_ERROR`), and a direction the source does not move (422 `INVALID_LEDGER_ROW` — `other_income` is always `in`, `other_expense` always `out`, `expense_reimbursement` always `out`; a reversal is exempt, because a reversal of `dues` is an `out` row). It refuses any row dated inside a closed period (409 `PERIOD_CLOSED` with `details {period_name}`). It never commits on its own: the caller owns the transaction, so a ledger row and the state change that caused it are one atomic write. Every Phase 1–5 writer (dues, tickets, merch, fundraiser income) was moved behind it in this phase, and `scripts/seed.py` is the only caller allowed to pass an explicit past `occurred_at` — through a plainly named seed-only parameter (`seed_backdate`), never on a public route.
    - **The books have one arithmetic, written once.** In `services/ledger.py`: `total_in = SUM(in ∧ ¬reversal) − SUM(out ∧ reversal)`, `total_out = SUM(out ∧ ¬reversal) − SUM(in ∧ reversal)`, `balance = total_in − total_out`. A reversal therefore cancels its original by subtracting from the side the original moved, and every report — summary, per-source, per-event, per-month, the running balance in the ledger table — is built from these three expressions so no report can invent its own arithmetic. `reconcile()` recomputes four streams straight from the tables that caused them (`dues`, `tickets`, `merch`, `expense_reimbursement`) and compares each with the ledger, then adds three boolean checks: every reimbursed claim has exactly one ledger row, every ledger amount is positive, and the balance is not negative. It returns `{ok, checks: [{name, ledger_total, source_total, difference, ok}]}`; `difference` is `ledger − source`, and it is zero when the stream is healthy.
    - **A receipt is not a URL, it is a private object behind a signed URL.** Uploads are validated once, in one function: JPEG/PNG/WebP/PDF only, max 5 MB, and the check is on **magic bytes**, not the client's `Content-Type` (413 `FILE_TOO_LARGE`, 422 `INVALID_FILE_TYPE`). The stored key is `receipts/{claimant_id}/{expense_id}/{uuid4}.{ext}` — the client's filename is **never** used and **never** stored. Reading a receipt is `GET /expenses/{id}/receipt`, which mints a signed URL that expires in 10 minutes: the path is never returned by any endpoint, and the bucket is **private**, because a receipt is a photograph of somebody's till slip. `STORAGE_PROVIDER=local` writes to `LOCAL_STORAGE_DIR` for dev and tests, `supabase` talks to Storage with the service-role key (10-second timeout, one retry on 5xx); the key is never logged and never returned. `scripts/setup_storage.py` creates the private bucket idempotently and fails if it finds the bucket public.
    - **A receipt is optional to submit and required to approve.** A volunteer filing a claim from a queue may not have the bill to hand yet, so `POST /expenses` accepts a claim with no receipt; `PATCH /expenses/{id}/review` with `approve` refuses one (409 `RECEIPT_REQUIRED`). Approval is the signature on a document, and there is no document.
    - **The claimant owns a claim only until it is decided.** Edit and replace-receipt and withdraw work while the claim is `submitted` or `rejected` (409 `INVALID_STATE` otherwise — once a treasurer has decided, the claim is theirs to pay). **Editing a rejected claim reopens it**: the status goes back to `submitted`, the review fields are cleared, and a `resubmitted` history row is written, so "handed back" and "sent again" are both on the record. Replacing a receipt deletes the old object rather than orphaning it.
    - **Nobody decides their own claim, whatever their rank.** `review` and `reimburse` both refuse when the actor is the claimant (409 `SELF_REVIEW`) — including an admin or a treasurer. Only a `submitted` claim can be approved or rejected, a rejection needs a note of 5+ characters ("no" is not feedback), and only an `approved` claim can be paid. Both decisions take `SELECT ... FOR UPDATE OF expenses` with `populate_existing`, so two treasurers clicking at the same instant resolve to one approval and one 409 — the second one reads the status the first one wrote, not the stale copy in its own session.
    - **Paying a claim is one transaction: lock the row, check the funds, write the `out` row, fill `ledger_transaction_id`.** Paying the same claim twice is a **replay**, not a second payment: a claim already `reimbursed` returns the stored result and writes nothing. A claim larger than the balance is 409 `INSUFFICIENT_FUNDS` with `details {balance, amount}` so the UI can say how short it is; `allow_negative=true` overrides it and is **admin-only** (403 `FORBIDDEN` for a treasurer or a hand-logged manual entry). A claim is paid with a `method` (`cash|upi|bank_transfer`) and an optional reference, both recorded.
    - **Visibility follows the money.** A claimant sees their own claims; treasurer and above see every claim (the review queue, with per-status counts and the two totals that matter: `submitted_amount` waiting for a decision and `approved_unpaid_amount` owed). Organizer and volunteer see neither other people's claims nor any finance route — `GET /finance/*` is treasurer+, and reopening a closed period is admin-only.
    - **The finance surface is read-mostly and every write is deliberate.** `GET /finance/summary` (window totals, by source, by category, by month, pending reimbursements), `GET /finance/transactions` (the ledger table: date/source/direction/event/fundraiser/text filters, a `label` a human can read, the actor, and a `running_balance` when sorted ascending — computed as a window over the **whole** ledger, so a filtered page still shows the true running total), `GET /finance/by-event` and `by-fundraiser` (grouped, one query each — never one per row), `GET /finance/outstanding-reimbursements` (who is waiting, how much, since when), `GET /finance/report` (the semester report) and `GET /finance/reconcile`. The only writes are `POST /finance/transactions` (a hand-typed `other_income`/`other_expense`, honouring an `Idempotency-Key`, backdatable at most 60 days and never into the future) and `POST /finance/transactions/{id}/reverse`.
    - **`GET /finance/report` asserts its own arithmetic.** `opening_balance` is the balance of everything strictly before `from`, `net_movement` is `total_in − total_out` inside the range, and the service **asserts** `opening + net == closing` before returning — a report that does not add up is a 500, not a plausible-looking PDF. It carries the income and expense breakdowns, `by_event`, `by_fundraiser`, outstanding reimbursements, the top expenses, and its own `reconciliation` block, so a printed report shows its work.

| POST | /fundraisers/{id}/tasks | organizer+ | 201; `{title 3–120, description?, category ("other"), assignee_id?, due_date?, status ("todo")}`. The card lands at the **bottom** of its column. 422 `INVALID_ASSIGNEE` (not an active volunteer+), 422 `DUE_AFTER_EVENT` (due after the day it is being prepared for), 409 `FUNDRAISER_CLOSED` |
| GET | /tasks | volunteer+ | every board at once. Filters `fundraiser_id`, `event_id`, `status`, `assignee_id`, `category`, `overdue=true`, `q`; `sort=board` (default) or `sort=due_date` (undated cards last) |
| GET | /tasks/me | volunteer+ | **my cards across every board, overdue first** — the volunteer's whole workload, not one fundraiser's |
| GET | /tasks/{id} | volunteer+ | 404 `TASK_NOT_FOUND` |
| PATCH | /tasks/{id} | volunteer+ | **and the rule is per-card, in the service:** organizer+ for any field, or the card's own assignee **for `status`/`position` only** — anyone else gets 403 `FORBIDDEN` with `details {fields}`. `{title?, description?, category?, assignee_id?, due_date?, status?}`; setting `status` to `done` stamps `completed_at` |
| POST | /tasks/{id}/move | volunteer+ | `{status, position?}` — the drag-and-drop write; organizer+, **or the card's own assignee**. `position` is clamped into range and omitted means the bottom; both columns are re-indexed densely |
| DELETE | /tasks/{id} | organizer+ | 204. Writes an `edited`/`deleted` activity row first and keeps it (`task_activity.task_id` → NULL, the title in `to_value`) |
| GET | /tasks/{id}/activity | volunteer+ | paginated trail, **newest first**: `{id, task_id, actor{id, full_name, role}, action, from_value, to_value, created_at}` |
| GET | /fundraisers/{id}/volunteers | volunteer+ | who is on this board: `{user{id, full_name, role}, tasks_total, tasks_done, open_tasks}` — unassigned cards are nobody's |
| GET | /users/assignable | organizer+ | the assignee picker: active **volunteer and above** only, A–Z: `{id, full_name, email, role}`. A member cannot be handed club work |
| POST | /fundraisers/{id}/income | organizer+ | 201 → `{id, amount, note, occurred_at, raised_total, percent_of_goal, replayed}`. Body `{amount 1–10,000,000 paise, note?, source_label?, occurred_at?}`; the ledger note is `source_label - note`. **Honours an `Idempotency-Key`** (§4 rule 13): the same key returns the row it already wrote with `replayed: true`. 422 for a bad amount or an impossible date, 409 `FUNDRAISER_CLOSED` more than 7 days after `completed_at` |
| GET | /fundraisers/{id}/income | volunteer+ | the cash book, **newest first**: `{id, amount, note, occurred_at, logged_by{id, full_name, role}, created_at}` |

**Progress shape** (`GET /fundraisers/{id}`): `{tasks: {total, todo, doing, done, overdue, due_soon, unassigned, percent_done}, raised, spent, net_raised, goal, percent_of_goal, days_to_event, health, by_category[{category, total, done}], by_assignee[{assignee_id, name, total, done}]}`. `overdue` is past `due_date` and not done, `due_soon` is due within 3 days, `unassigned` counts only open cards, `days_to_event` goes negative once the date has passed, and `percent_done` is `0` on an empty board rather than a division error. `health` is `on_track` / `at_risk` / `behind` / `completed` (§4 rule 13) — the frontend renders the colour from this word alone, so the thresholds live in one place.

**Added in Phase 6:** `spent` is the money the club paid out against this fundraiser — the sum of its `expense_reimbursement` ledger rows, i.e. claims charged to it through `expenses.fundraiser_id` — and `net_raised` is `raised − spent`. **`raised` stays gross**, so a frontend mock that divides `raised` by `goal` keeps its meaning and no existing UI changes behaviour; `net_raised` is the honest number a treasurer wants. `spent` is `0` for a fundraiser nobody has claimed against.

**What is NOT here, on purpose:** no DELETE for a fundraiser, no edit and no delete for an income row, no endpoint that writes a `task_activity` row directly, and no public ledger endpoint — the money is read through `GET /fundraisers/{id}/income` for one fundraiser, and through the treasurer's finance routes for everything else.

### Payments
Which provider is live is a setting, not a code path: `PAYMENTS_PROVIDER=mock|razorpay` in `.env` (`backend/.env.example` documents the keys). The order, membership, ticket, stock and ledger code behind a confirmation is identical either way — none of it knows where the confirmation came from (§4 rule 3).

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | /payments/{order_id} | auth, owner or admin | **what the checkout page needs to open the gateway, and to redraw itself after a reload or a redirect back from a bank page** (where the SPA's router state is gone). `{order_id, kind, order_status, amount, currency, provider, payment_status, key_id, gateway_order_id}`. `key_id` and `gateway_order_id` are both `null` under the mock provider and both set under Razorpay; `amount` is integer paise |
| POST | /payments/{order_id}/verify | auth, owner or admin | the Checkout widget's success callback: `{razorpay_order_id, razorpay_payment_id, razorpay_signature}`. The signature covers `order_id|payment_id` with the **API key secret**, so a client that invents these gains nothing. Returns the same body as `mock-confirm`. 400 `INVALID_SIGNATURE`, 400 `ORDER_MISMATCH` when the callback names a different order, 409 `NOT_A_GATEWAY_PAYMENT` on a mock order. Settles through the same idempotent claim as the webhook, so whichever of the two arrives first settles and the other replays |
| POST | /payments/webhook | **public**, signature-verified | the gateway calls this. `X-Razorpay-Signature` is an HMAC-SHA256 of the **raw body** with `RAZORPAY_WEBHOOK_SECRET`; it is verified **before anything is parsed** (the raw bytes are read off the request, not the bound model) and 400 `INVALID_SIGNATURE` is the only answer to a body without one — an unverified webhook would be a free-money endpoint. `payment.captured` and `order.paid` settle, `payment.failed` fails the order, anything else is acknowledged and ignored (`{status: "ignored"}`) so it is not retried forever. 404 `PAYMENT_NOT_FOUND` for a gateway order we never created, 400 `AMOUNT_MISMATCH` when the paid amount is not the ordered amount (money moved, but not ours to ledger — refuse loudly rather than record a wrong number). Always 200 on a no-op |
| POST | /payments/{order_id}/mock-confirm | auth, owner or admin | **mock provider only.** Body `{outcome: "success"\|"fail"}` simulates the gateway; 409 `SIMULATED_PAYMENT_DISABLED` when `PAYMENTS_PROVIDER` is not `mock`, because on a live deployment nobody may settle an order by asserting an outcome. Returns `{order_id, payment_id, order_status, payment_status, provider_ref, membership, tickets, merch}` — the dispatcher keys off `order.kind`, so a `membership` order fills `membership` (and leaves `tickets`/`merch` `null`), a `ticket` order fills `tickets`, and a `merch` order fills `merch` = `{order_id, fulfilment_status, delivery_method, delivery_note, packed_at, handed_over_at}` (the others stay `null`). Safe to call twice: the second call returns the same body and changes nothing (§4 rule 3). On `fail`: payment `failed`, order `failed`, membership untouched, tickets' seats released and merch stock released once (§4 rule 12). Cancelling an order the sweep already expired → 409 `ORDER_NOT_PAYABLE` whichever outcome is sent, because its stock is already back on the shelf. An order that already **failed** is not an error: a repeat `fail` releases nothing further (one `release` movement, never two) and a `success` aimed at it cannot revive it — the claim finds no `pending` row and the stored failure is replayed. No path pays for stock that has gone back |

**`payments.provider_ref` holds the gateway's id for the attempt** — under Razorpay that is the **order** id (`order_...`), because it is what every event and callback carries, so it is what an incoming request can look the row up by; under the mock provider it is minted locally at settlement. The Razorpay **payment** ids seen against it are appended to `raw.payments[]` instead, never overwriting: a customer who retries after a failure can produce two, and a duplicate charge is exactly what the treasurer has to be able to see.

**Idempotency is the conditional claim, not the id.** A retried webhook, the widget's callback racing that webhook, and `order.paid` arriving after `payment.captured` all describe one payment, and all four land on `UPDATE orders SET status='paid' WHERE id=:id AND status='pending'` — the winner does the work, the losers replay the stored result. There is no window in which the same money is fulfilled twice.

**Refunds are not here yet** (M2 backlog §1): they arrive as a new ledger row with `direction: "out"` and `source: "refund"` linking back to the original, never as an edit of it — the ledger is immutable.

## 6. Frontend Design

### Design language
Clean, modern campus-club feel. Primary: deep indigo `#4338CA`; accent: amber `#F59E0B`; success green, danger red; neutral slate. Font: Inter. Rounded-xl cards, soft shadows, generous spacing. Mobile-first, dark mode optional (M2). Skeleton loaders, toasts, empty states with illustrations, form validation messages inline.

### Route map
**Public:** `/` landing (hero, next event, latest announcement, join CTA) · `/events` · `/events/:id` · `/announcements` · `/announcements/:id` · `/unsubscribe` (target of the email footer link, reads `?token=`) · `/shop` · `/shop/:id` · `/join` (plans) · `/login` · `/register`
**Member:** `/me` dashboard (membership status/renew banner, QR member card, upcoming tickets) · `/me/tickets` · `/me/orders` · `/checkout/:orderId`
**Staff:** `/staff/scan` (door scanner, big green/red result, event picker) · `/staff/verify-member`
**Organizer:** `/manage/events` (+ create/edit, ticket types, report) · `/manage/announcements` · `/manage/fundraisers` (+ `/:id` kanban board) 
**Admin:** `/admin/members` · `/admin/plans` · `/admin/renewals` · `/admin/products` · `/admin/merch-orders` · `/admin/users`
**Treasurer:** `/finance` dashboard (cards + charts + tables) · `/finance/expenses` review queue · `/finance/ledger` · `/finance/report` (printable)
**Volunteer:** `/tasks` (my tasks) · `/expenses/new`

### Key screen specs
- **Event page:** banner, date/venue, ticket type cards showing member vs non-member price (highlight the one that applies to the viewer), "seats left" progress bar, sold-out state.
- **Door scanner:** camera scan + manual code field; full-screen result colour (green VALID / amber ALREADY USED w/ time / red INVALID); live counter "checked in 87 / 120".
- **Member card:** QR + name + status chip (Active until DD MMM YYYY).
- **Kanban:** 3 columns, drag between columns, assignee avatars, due-date chips (red if overdue), progress ring on top + raised-vs-goal bar.
- **Treasurer dashboard:** 4 KPI cards (In, Out, Balance, Pending reimbursements), donut by source, bar by category, recent transactions, per-event profit table.
- **Shop:** product grid, size selector with per-size stock ("Only 3 left"), cart drawer, mobile-friendly checkout.
- **Checkout:** `/checkout/:orderId` serves membership, ticket and merch orders alike. It reads `GET /payments/{order_id}` rather than trusting the router state it was navigated with, so a reload — or a return from a bank page, which loses that state — still shows the right order at the right amount. Under `PAYMENTS_PROVIDER=razorpay` it opens the Razorpay Checkout widget and settles through `POST /payments/{order_id}/verify`; the simulated success/failure buttons exist only under `mock`, and are the only place the word "mock" reaches a member.

### Frontend rules
- API client in `src/api/` generated from types matching this contract; all money displayed via `formatINR(paise)`.
- Use TanStack Query; auth token in memory + refresh via `localStorage` (M1 acceptable).
- Until backend phase endpoints land, use **mock handlers (MSW)** matching this contract; switch with `VITE_USE_MOCKS=false`.

**Fundraisers & tasks (Phase 5):** three fundraisers, built through the **real** services so their activity trails are real too. **Spring Bake Sale** (goal ₹5,000, active, owned by the seeded organizer) with 8 cards — 3 done, 2 doing, 3 todo of which 2 have nobody on them and one is overdue — which is exactly the shape that makes `health` read `at_risk`, and ₹2,000 of income logged as "Pre-orders" and "Morning sales" (40% of goal). **Book Drive** in `planning` with 2 cards, to show a board that has not started. **Diwali Stall** finished and past: all cards done, ₹2,500 logged, `completed_at` twenty days ago — so its board is read-only and its income window (7 days) is closed, which is the state most demos forget to stage. The seed prints the fundraiser and ledger counts, and left no closed finance period behind.

**Expenses & finance (Phase 6):** seven claims totalling **₹9,220** across four claimants (`volunteer`, `neha`, `rohit`, `organizer`) and seven categories (`travel`, `printing`, `food`, `equipment`, `supplies`, `venue`, `marketing`), each walked through the **real** service so `expense_history` holds the same rows the API would write. The states are staged deliberately: two `reimbursed` (each with exactly one `expense_reimbursement` ledger row and a `ledger_transaction_id`), one `approved` but not yet paid, two sitting in the treasurer's queue as `submitted`, one `rejected` with a review note, and one `withdrawn` by its own claimant. Five carry receipts — generated in-memory at seed time, two PNGs and two PDFs plus one more, never committed as binaries — and the two `submitted` claims are receiptless on purpose, which is the state `RECEIPT_REQUIRED` blocks at approval. A hand-logged quarter of history spreads the ledger over ~90 days: `other_income` ₹5,000 "Sponsor - campus bookstore", `other_expense` ₹800 "Banner printing", three more `other_income` rows in `HISTORY_SEED` (July canteen share, a returned merch float, a 2019 alumni donation) and **one reversal** of the ₹800 banner bill, so `reconcile()` has a reversal to cancel rather than an empty set. Those past dates go through the writer's seed-only `seed_backdate` parameter — the public API never accepts an arbitrary past `occurred_at` beyond the 60-day manual-entry window. The seed leaves **no finance period behind** (a closed period would make later demos fail with `PERIOD_CLOSED`), and finishes by asserting `finance_service.reconcile(db)["ok"]`, which is the "balance is not negative / every reimbursed claim has exactly one ledger row / opening + net == closing" check the tests check. After a clean run the books read balance **₹97,139** and reconcile 7/7.
