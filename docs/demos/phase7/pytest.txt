How the shuffled run is done, and why not the obvious way
---------------------------------------------------------
The first attempt collected the node ids with `--collect-only -q` and replayed
them into a second pytest process. It reported EXIT=4 in 0.40s -- pytest's usage
error -- and ran zero tests. The reason is in this suite:

  tests/test_hardening.py:66    FAKE_ID = str(uuid4())

`test_framework_errors_use_the_envelope` parametrises over that constant, so its
node id is

  ...envelope[GET-/api/v1/events/<a fresh uuid4>/ticket-types-METHOD_NOT_ALLOWED]

Different in every process. An id collected in one process therefore cannot
exist in the next, and pytest 9 refuses to collect anything at all when one
argument does not resolve -- so the gate looked like a red suite when in truth
it had never executed a single test.

The run above shuffles the item list inside one session instead, via a throwaway
plugin loaded with `-p` (never imported by an ordinary run, and deleted after
this file was written). Sampled collection order confirms it takes effect: the
unshuffled first test is test_announcements.py::test_guard_refuses..., the
shuffled first is test_fundraisers.py::test_write_permissions[guest-patch-...].

Worth remembering beyond this phase: `--collect-only` ids are not replayable for
any suite with a parametrize over a per-process value. Normal `pytest -q` runs
are unaffected, so the test was left alone.
